# استقرار ویراستار پژوهش روی Render

مخزن کد: https://github.com/seyyedahmadmousavi0-spec/virastar-thesis-bot

سرویس موجود: https://virastar-thesis-bot.onrender.com

## آماده‌سازی سرویس موجود

۱. در تنظیمات سرویس Render، مخزن بالا و شاخهٔ `main` را بررسی کنید. برای همین سرویس موجود کار کنید؛ ساخت سرویس دوم باعث اجرای هم‌زمان دو دریافت‌کنندهٔ پیام برای یک توکن می‌شود.

۲. در بخش Environment، متغیر `BALE_TOKEN` باید مقدار معتبر داشته باشد. نسخهٔ ۲ توکن را فقط از محیط می‌خواند؛ `.env` و توکن به GitHub یا تصویر Docker وارد نمی‌شوند. توکنی که قبلاً در کد عمومی قرار گرفته باید در مدیریت ربات بله تعویض شود و مقدار جدید فقط در تنظیمات محرمانهٔ Render ثبت شود.

۳. برای runtime از Dockerfile ریشهٔ مخزن استفاده کنید. دستور اجرا `python bot.py` است. اگر سرویس از runtime بومی Python استفاده می‌کند، Python 3.12، دستور ساخت `python -m pip install -r requirements.txt` و همین دستور اجرا را تنظیم کنید. دستور قدیمی `python web_runner.py` نیز به همان نقطهٔ شروع هدایت می‌شود.

۴. `PORT=10000`، یک نمونهٔ سرویس، و Health Check Path برابر `/ready` تنظیم کنید. مقدارهای `WORKERS=2` و `MAX_QUEUE=4` نقطهٔ شروع کم‌مصرف‌تری نسبت به پیش‌فرض محلی‌اند؛ با توجه به حافظه و حجم اسناد تنظیم شوند. `BALE_SKIP_DOTENV` برای آزمون است و در سرور لازم نیست.

۵. Auto-Deploy را روی **After CI Checks Pass** بگذارید. گردش‌کار Precision چهار ترکیب Windows/Linux و Python 3.12/3.14 را بررسی می‌کند. سرویس‌های متصل به مخزن عمومی بدون اتصال حساب Git ممکن است نیازمند استقرار دستی باشند.

## انتشار و تأیید

با Auto-Deploy برابر **After CI Checks Pass**، پس از موفقیت هر چهار اجرای آزمون، Render کامیت جدید را خودکار مستقر می‌کند. استقرار دستی فقط برای بازیابی یا شرایطی است که اتصال خودکار در دسترس نباشد. اگر پیام کامیت شامل `[skip render]` باشد، استقرار خودکار آغاز نمی‌شود.

این نشانی‌ها را بررسی کنید:

- `/health`: پاسخ HTTP 200 برای فرایند زنده، همراه `version` و `revision`؛
- `/ready`: پاسخ HTTP 200 و `ready: true` پس از ارتباط موفق و تازه با بله؛ در وضعیت آماده‌نبودن HTTP 503؛
- `version` باید با نسخهٔ انتشار موردنظر و `revision` باید با SHA کامیت آن در GitHub مطابقت داشته باشد. Render مقدار `RENDER_GIT_COMMIT` را به فرایند می‌دهد.

برای بررسی رفتاری، در بله `/start` و سپس یک سند آزمایشی غیرمحرمانه ارسال کنید. DOCX باید بدون توضیح `/annotate` یک کپی مستقل Word با کامنت‌های قابل تطبیق بدهد؛ چت فقط خلاصهٔ A/B/C و تعداد واقعی کامنت‌ها دارد. `/report` و دکمهٔ گزارش کامل باید HTML و TXT آخرین بررسی همان فرستنده در همان گفت‌وگو را بدهند. PDF پیش‌فرض گزارش متنی صفحه‌دار دارد. پاسخ سلامت نباید شناسهٔ گفت‌وگو، متن پیام، توکن یا مسیر سند را نمایش دهد.

تنظیمات نسخهٔ ۲.۱: `MAX_COMMENTS=250` (۱ تا ۱۰۰۰)، `REPORT_TTL_MINUTES=15` (۱ تا ۶۰) و `REPORT_CACHE_MB=32` (۱ تا ۱۲۸). گزارش‌ها فقط در حافظه نگهداری می‌شوند، با `/forget` پاک می‌شوند و راه‌اندازی مجدد آن‌ها را از بین می‌برد. پاک‌سازی حافظه هر ۳۰ ثانیه است؛ دریافت پس از زمان انقضا مجاز نیست. `PDF_ANNOTATION_EXPERIMENTAL=0` را تا تأیید مستقل نمایش و محل یادداشت‌های فارسی حفظ کنید؛ این قابلیت به سرویس جدید یا وابستگی تازه نیاز ندارد.

در صورت شکست استقرار، لاگ‌های Render را بدون انتشار توکن بررسی کنید. تا آماده‌شدن نسخهٔ جدید، استقرار سالم قبلی را حفظ کنید. نسخهٔ قدیمی موجود در تاریخچه توکن تعبیه‌شده داشته است؛ برای بازگشت، نسخه‌ای با توکن داخل کد را دوباره مستقر نکنید.

## نگهداری

گردش‌کار `Render readiness monitor` هر پنج دقیقه (در دقیقه‌های ۲، ۷، ۱۲ و … به وقت UTC) برای `/ready` درخواست می‌فرستد. پاسخ باید JSON معتبر، `ready: true` و دریافت پیام فعال را نشان دهد؛ صفحهٔ بارگذاری یا صرف HTTP 200 موفقیت محسوب نمی‌شود. برای بیدارشدن سرویس شش تلاش محدود انجام می‌شود. شکست در صفحهٔ Actions ثبت می‌شود؛ ارسال اعلان تابع تنظیمات GitHub کاربر است.

Render رایگان پس از ۱۵ دقیقه بدون ترافیک HTTP ورودی می‌تواند بخوابد؛ بیدارشدن طبق مستندات حدود یک دقیقه است و زمان ثابتی ندارد. درخواست خروجی `getUpdates` به بله، ترافیک ورودی Render نیست؛ پیام جدید در بله به‌تنهایی سرویس خوابیده را بیدار نمی‌کند. پینگ داخلی `KEEP_ALIVE_URL` هم پس از خواب اجرا نمی‌شود و بازیابی مستقل نیست.

زمان‌بندی GitHub ممکن است دیر اجرا یا حذف شود و در مخزن عمومی پس از ۶۰ روز بی‌فعالیتی خودکار غیرفعال شود. سهمیهٔ ۷۵۰ ساعت رایگان ماهانه بین همهٔ سرویس‌های رایگان همان workspace مشترک است؛ روشن‌نگه‌داشتن چند سرویس می‌تواند سهمیه را تمام کند. بنابراین پایش رایگان تضمین شبانه‌روزی نیست. پلن محاسباتی پولی سرویس محدودیت خواب بیکاری را حذف می‌کند؛ تغییر پلن هزینه‌دار فقط با تأیید مالک انجام می‌شود و تضمین نبود هرگونه قطعی نیست.

تنها یک فرایند polling برای این توکن اجرا شود؛ هم‌زمان نسخهٔ محلی را راه‌اندازی نکنید. تغییر فقط در پایش به بازسازی کانتینر ربات نیاز ندارد و می‌تواند با کامیت `[skip render]` منتشر شود.
