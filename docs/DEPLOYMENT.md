# استقرار ویراستار پژوهش روی Render

مخزن کد: https://github.com/seyyedahmadmousavi0-spec/virastar-thesis-bot

سرویس موجود: https://virastar-thesis-bot.onrender.com

## آماده‌سازی سرویس موجود

۱. در تنظیمات سرویس Render، مخزن بالا و شاخهٔ `main` را بررسی کنید. برای همین سرویس موجود کار کنید؛ ساخت سرویس دوم باعث اجرای هم‌زمان دو دریافت‌کنندهٔ پیام برای یک توکن می‌شود.

۲. در بخش Environment، متغیر `BALE_TOKEN` باید مقدار معتبر داشته باشد. نسخهٔ ۲ توکن را فقط از محیط می‌خواند؛ `.env` و توکن به GitHub یا تصویر Docker وارد نمی‌شوند. توکنی که قبلاً در کد عمومی قرار گرفته باید در مدیریت ربات بله تعویض شود و مقدار جدید فقط در تنظیمات محرمانهٔ Render ثبت شود.

۳. برای runtime از Dockerfile ریشهٔ مخزن استفاده کنید. دستور اجرا `python bot.py` است. اگر سرویس از runtime بومی Python استفاده می‌کند، Python 3.12، دستور ساخت `python -m pip install -r requirements.txt` و همین دستور اجرا را تنظیم کنید. دستور قدیمی `python web_runner.py` نیز به همان نقطهٔ شروع هدایت می‌شود.

۴. `PORT=10000`، یک نمونهٔ سرویس، و Health Check Path برابر `/ready` تنظیم کنید. مقدارهای `WORKERS=2` و `MAX_QUEUE=4` نقطهٔ شروع کم‌مصرف‌تری نسبت به پیش‌فرض محلی‌اند؛ با توجه به حافظه و حجم اسناد تنظیم شوند. `BALE_SKIP_DOTENV` برای آزمون است و در سرور لازم نیست.

۵. Auto-Deploy را روی **After CI Checks Pass** بگذارید. گردش‌کار Precision چهار ترکیب Windows/Linux و Python 3.12/3.14 را بررسی می‌کند. سرویس‌های متصل به مخزن عمومی بدون اتصال حساب Git ممکن است نیازمند استقرار دستی باشند.

## انتشار و تأیید

پس از موفقیت آزمون‌ها، در Render گزینهٔ **Manual Deploy → Deploy latest commit** را اجرا کنید. اگر پیام کامیت شامل `[skip render]` باشد، انتشار در GitHub استقرار خودکار Render را آغاز نمی‌کند؛ این روش برای آماده‌کردن متغیرهای محیطی پیش از اولین ارتقای نسخهٔ ۲ استفاده می‌شود.

این نشانی‌ها را بررسی کنید:

- `/health`: پاسخ HTTP 200 برای فرایند زنده، همراه `version` و `revision`؛
- `/ready`: پاسخ HTTP 200 و `ready: true` پس از ارتباط موفق و تازه با بله؛ در وضعیت آماده‌نبودن HTTP 503؛
- `version` باید با نسخهٔ انتشار موردنظر و `revision` باید با SHA کامیت آن در GitHub مطابقت داشته باشد. Render مقدار `RENDER_GIT_COMMIT` را به فرایند می‌دهد.

برای بررسی رفتاری، در بله `/start` و سپس یک متن یا سند آزمایشی غیرمحرمانه ارسال کنید. گزارش HTML و TXT باید برگردند؛ فایل Word علامت‌گذاری‌شده فقط با توضیح `/annotate` درخواست می‌شود. پاسخ سلامت نباید شناسهٔ گفت‌وگو، متن پیام، توکن یا مسیر سند را نمایش دهد.

در صورت شکست استقرار، لاگ‌های Render را بدون انتشار توکن بررسی کنید. تا آماده‌شدن نسخهٔ جدید، استقرار سالم قبلی را حفظ کنید. نسخهٔ قدیمی موجود در تاریخچه توکن تعبیه‌شده داشته است؛ برای بازگشت، نسخه‌ای با توکن داخل کد را دوباره مستقر نکنید.

## نگهداری

پینگ زمان‌بندی‌شدهٔ GitHub برای تشخیص پاسخ HTTP شکست را گزارش می‌کند، اما تضمین دسترس‌پذیری شبانه‌روزی یا زمان دقیق اجرا نیست. از پایش و طرح میزبانی مناسب نیاز عملیاتی استفاده کنید. تنها یک فرایند polling برای این توکن اجرا شود؛ هم‌زمان نسخهٔ محلی را راه‌اندازی نکنید.
